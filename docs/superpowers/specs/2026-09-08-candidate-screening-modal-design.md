# Дизайн — «Обработка кандидатов» (модалка HR-скрининга по портрету)

**Статус:** согласован владельцем 2026-09-08. Ревью архитектурных рисков проведено
2026-09-08 (findings внесены в текст ниже), открытые вопросы закрыты владельцем
2026-09-08/09. Заведён эпик **E15** (`05_EPICS.md`) — ждёт запуска реализации.
**Заменяет подход шага** `epics/E14-video-transcription-worker/step-E14-06-hr-ui.md`
**для сценария массового скрининга** — сам шаг E14-06 (транскрипт видео в карточке
одного кандидата) остаётся отдельно, не пересекается с этим дизайном.

## Контекст / зачем

Есть работающий backend-пайплайн скрининга (E10 CLI `run_full_course_screening.py`):
резюме → факты → fit-scoring по вакансии, с zip-выгрузкой прошедших порог. Но он
запускается вручную с консоли, без UI, без фонового переиспользования. Владелец хочет
UI-флоу поверх этого же ядра: HR редактирует текст-портрет вакансии прямо в интерфейсе,
запускает фоновую обработку всех кандидатов курса, видит ранжированный список
подходящих (fit_score ≥ 60, то есть ≥6/10), может выгрузить карточку одного кандидата
или пачкой, и не путается, кого уже передавал заказчику.

## Поток

1. HR открывает раздел кандидатов конкретного курса/вакансии в `SPHERA`. Видит кнопку
   «Обработка кандидатов» рядом с существующей «Выгрузить архив».
2. Клик → модалка:
   - textarea текста-портрета, предзаполненная текущим `VacancyProfile.requirements`
     этого курса (если версия уже есть);
   - список кандидатов с `fit_score ≥ 60` (отображается округлённо как X/10),
     отсортированный по убыванию;
   - у кандидатов, которых уже выгружали — бейдж «уже передан»;
   - на каждого кандидата — кнопка «выгрузить карточку»; отдельно — «выгрузить список»
     (пачкой, переиспользует существующий `export/`, E9-03).
3. HR правит текст портрета → «Сохранить» (в интерфейсе SPHERA) → запрос идёт в
   **FullSphera backend** (новый проксирующий endpoint, не напрямую в SFERA-AI —
   см. раздел «Авторизация и межсервисный вызов» ниже) → FullSphera backend вызывает
   `POST .../vacancy-profile/` в SFERA-AI:
   - backend SFERA-AI создаёт новую версию `VacancyProfile` (`create_vacancy_profile_version`,
     уже есть, E1-07) — это уже триггерит `enqueue_fit_recalc_for_course` (E7-04) для
     уже проанализированных кандидатов;
   - **плюс новый вызов** `enqueue_full_screening_for_course(course_id)` — ставит
     `AIProcessingJob` на **всех** кандидатов курса, включая тех, кто ещё ни разу не
     анализировался по этой вакансии. Выполняется **асинхронно, фоново** (не в теле
     HTTP-ответа на `POST vacancy-profile/`) — на курсах с сотнями кандидатов (реальный
     случай — до 500 в одном демо) синхронный перебор внутри запроса рискует таймаутом.
     Ответ HR приходит сразу после создания версии портрета, постановку задач разбирает
     воркер отдельным тиком (по образцу существующего scheduler'а, E5-04).
   - повторное «Сохранить» (двойной клик, две вкладки) не должно создавать дублирующие
     `AIProcessingJob` на одного кандидата — см. риск в разделе «Известные риски реализации».
4. Модалка закрывается сразу после сохранения — **без живого обновления прогресса**
   (согласовано явно). Существующий scheduler (E5-04, тик каждые 30 мин) разбирает
   очередь как обычно.
5. HR открывает модалку позже — видит обновившийся список по `GET
   .../candidates/screening/`.
6. Выгрузка карточки (одной или списком) автоматически помечает кандидата(ов) как
   «передан» — не требует отдельного действия от HR.

Существующий CLI `run_full_course_screening.py` (E10) не меняется — остаётся
независимым инструментом для ручных прогонов без UI.

## Данные

Новая таблица `CandidateVacancyTransfer` (репозиторий `SFERA-AI`, Alembic-миграция):

| Поле | Тип | Комментарий |
|---|---|---|
| `id` | PK | |
| `candidate_profile_id` | FK → `CandidateProfile` | |
| `course_id` | Integer | id курса на платформе (как в остальных вакансийных джобах) |
| `transferred_at` | timestamp | когда впервые выгружен |

Уникальный индекс на `(candidate_profile_id, course_id)` — повторная выгрузка не
дублирует запись, **upsert обновляет `transferred_at` на текущее время** (решено
владельцем — поле должно отражать дату последней передачи, не первой; это же
согласуется с формулировкой edge case «повторно проставляет/подтверждает
`transferred_at`» ниже).

Отдельная таблица, а не поле на `CandidateVacancyAnalysis` — статус «передан» не должен
сбрасываться при пересчёте fit / появлении новой версии анализа (у `CandidateVacancyAnalysis`
своя версионная история, `is_current` меняется при каждом пересчёте).

Отображаемая шкала 6–10 в UI — **только форматирование**: `floor(fit_score / 10)`
(не `round` — с `round` диапазон 55–59 тоже отображался бы как «6/10», визуально
неотличимо от реально прошедших порог 60–64, хотя 55–59 в список не попадают; `floor`
даёт «6/10» ровно с того же значения, с которого кандидат проходит порог). Внутри всё
остаётся на шкале 0–100 (`fit_score` — `SmallIntegerField`, как сейчас). Порог показа в
модалке — `fit_score >= 60`.

## API (репозиторий `SFERA-AI`, слой `E8 Read API`)

- **`GET .../candidates/screening/`** (новый) — кандидаты курса с `fit_score >= 60`,
  сортировка по убыванию `fit_score`. Каждая запись — как в существующем `candidates/`
  списке (E8-02) + новое поле `transferred: bool` (join на `CandidateVacancyTransfer`).
- **`POST .../vacancy-profile/`** (существует, E8-04) — контракт не меняется. После
  `create_vacancy_profile_version` добавляется второй вызов —
  `enqueue_full_screening_for_course(course_id)` — рядом с уже существующим
  `enqueue_fit_recalc_for_course`.
- **`POST .../export/`** (существует, E9-03) — после сборки архива добавляется побочный
  эффект: upsert в `CandidateVacancyTransfer` **только для кандидатов, у которых
  реально собрался `card.pdf`** (то есть `render_ai_card_pdf` вернул не `None`) — не
  для всех id, переданных в запросе. `build_candidates_export_archive` не падает на
  недоступных файлах (пишет `manifest.txt` и продолжает), поэтому "кандидат попал в
  архив" и "кандидату реально есть что показать заказчику" — разные вещи; бейдж
  «передан» не должен появляться у кандидата, чья папка в zip пустая.

## Авторизация и межсервисный вызов

SFERA-AI не проверяет личность HR и его права на конкретный курс — весь API сервиса
защищён только общим `bff_shared_secret` (сервис-к-сервису, уже реализовано, E8-01),
рассчитанным на единственного доверенного вызывающего — backend FullSphera. Проверка
«у этого HR есть права на этот курс» должна происходить **на стороне FullSphera**, до
вызова SFERA-AI, тем же способом, что уже защищает существующую кнопку «Выгрузить
архив» — `CourseCandidatesManagementPermission` (`core/permissions.py`, company-scoped:
HR имеет доступ к любому курсу своей компании, персональной привязки HR→курс в
платформе нет и не появляется в рамках этой фичи).

Практическое следствие: фронтенд SPHERA не должен стучаться в SFERA-AI напрямую.
Нужен новый проксирующий endpoint в FullSphera backend (репозиторий `sfera_backend`,
по паттерну существующих `CandidateArchiveJob*View` в `courses/views.py`) с этим же
permission-классом — он сам вызывает SFERA-AI, используя `bff_shared_secret`. Это
новая работа на стороне FullSphera (новый view + новый HTTP-клиент по образцу
`integrations/headhunter/client.py` + новый секрет в settings/env) — см. эпик E15,
блок «FullSphera».

## Новая сервисная функция

`enqueue_full_screening_for_course(session, course_id)` — новая функция в
`src/sfera_ai/services/job_detection.py`. По образцу перебора `Application` из
`run_full_course_screening.py` (E10-01): для каждого кандидата курса —
`resolve_or_create_candidate_profile` (если профиля ещё нет) + постановка джобы через
уже существующий `_create_job_if_absent` (дедуп: не дублирует уже стоящую `PENDING`
джобу того же кандидата). Дальше существующий scheduler/воркер (E5-04) сам гоняет
обычный пайплайн (resume → facts → fit) — новый код ничего не знает про сам скоринг,
только ставит джобы.

## Frontend (репозиторий `SPHERA`) и проксирующий слой (репозиторий `sfera_backend`)

**Другие репозитории — требуют отдельного явного разрешения владельца на каждую
конкретную правку** (правило `CLAUDE.md` этого проекта, как и весь эпик E14).

- Кнопка «Обработка кандидатов» — в разделе кандидатов конкретного курса, рядом с
  «Выгрузить архив» (не глобально, не отдельный раздел).
- Модалка: textarea портрета + список из `GET .../candidates/screening/`, кнопки
  экспорта (одиночный/массовый).
- «Сохранить» → фронт вызывает **новый endpoint в FullSphera backend** (не SFERA-AI
  напрямую, см. «Авторизация и межсервисный вызов») → тот проксирует в
  `POST .../vacancy-profile/` SFERA-AI → закрыть модалку немедленно, без поллинга
  статуса.
- Аналогично `GET .../candidates/screening/` и `POST .../export/` — через
  проксирующие endpoint'ы FullSphera backend с тем же `CourseCandidatesManagementPermission`.

## Известные риски реализации (из архитектурного ревью 2026-09-08)

- **Гонка при двойном «Сохранить»**: постановка `AIProcessingJob` защищена от дублей
  только проверкой в коде приложения (`_create_job_if_absent`), не constraint'ом в БД —
  под конкурентным вызовом два запроса могут проскочить проверку одновременно и создать
  дублирующие джобы (двойной расход на LLM). На шаге реализации `enqueue_full_screening_for_course`
  — либо добавить partial unique index в БД + обработку `IntegrityError` как no-op,
  либо гвард на уровне нового FullSphera-endpoint'а (не дать второй `POST` уйти, пока
  предыдущий не завершился).
- **`pilot_course_id`-ограничение очереди** (`job_processing.py`, если оно будет
  включено на проде до релиза этой фичи) — сейчас непилотные джобы не исключаются из
  `SELECT`, а пропускаются постфактум, что может забивать очередь. Не блокирует эту
  фичу (переменная сейчас не выставлена, сервис ещё не в проде), но стоит поправить
  фильтрацию на уровне запроса до первого боевого запуска на непилотном курсе.

## Edge cases

- Открыли модалку только посмотреть список, портрет не трогали — «Сохранить» не жали →
  новых джоб не ставим, GET ничего не запускает, только читает текущее состояние.
- Нет ни одного кандидата с `fit_score >= 60` — модалка показывает пустое состояние, не
  ошибку.
- Кандидат без резюме (уже покрыто E13 — «нет резюме» не блокирует, только снижает
  уверенность) — попадает в список на общих основаниях, если fit ≥ 60.
- Повторное «Сохранить» без реальных правок текста — `create_vacancy_profile_version`
  создаст новую версию в любом случае (существующее поведение E1-07, не меняем в рамках
  этого дизайна); UX-предупреждение «текст не менялся» — вне объёма, можно обсудить
  отдельно на шаге фронтенда.
- Повторная выгрузка уже «переданного» кандидата — не ошибка, обновляет `transferred_at`
  на текущее время (см. «Данные» — зафиксировано, не «ничего не делает»).

## Вне объёма этого дизайна

- Живое обновление прогресса обработки в модалке (осознанно отклонено — «без живого
  обновления»).
- UX-предупреждение о бессмысленном пересохранении портрета без изменений.
- Изменение шкалы `fit_score` в БД/промпте (осталась 0–100, 6–10 — только отображение).
- Сам E14-06 (транскрипт/summary видео в карточке ответа кандидата) — отдельный шаг,
  не пересекается с этим дизайном.
