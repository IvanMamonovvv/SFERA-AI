# Дизайн — «Обработка кандидатов» (модалка HR-скрининга по портрету)

**Статус:** согласован владельцем 2026-09-08, ждёт запуска реализации (`writing-plans`).
**Заменяет подход шага** `epics/E14-video-transcription-worker/step-E14-06-hr-ui.md`
**для сценария массового скрининга** — сам шаг E14-06 (транскрипт видео в карточке
одного кандидата) остаётся отдельно, не пересекается с этим дизайном.

## Контекст / зачем

Есть работающий backend-пайплайн скрининга (E10 CLI `run_full_course_screening.py`):
резюме → факты → fit-scoring по вакансии, с zip-выгрузкой прошедших порог. Но он
запускается вручную с консоли, без UI, без фонового переиспользования. Владелец хочет
UI-флоу поверх этого же ядра: HR редактирует текст-портрет вакансии прямо в интерфейсе,
запускает фоновую обработку всех кандидатов курса, видит ранжированный список
подходящих (fit_score ≥ 60, то есть ≥6/10), может выгрузить карточку одного кандидата
или пачкой, и не путается, кого уже передавал заказчику.

## Поток

1. HR открывает раздел кандидатов конкретного курса/вакансии в `SPHERA`. Видит кнопку
   «Обработка кандидатов» рядом с существующей «Выгрузить архив».
2. Клик → модалка:
   - textarea текста-портрета, предзаполненная текущим `VacancyProfile.requirements`
     этого курса (если версия уже есть);
   - список кандидатов с `fit_score ≥ 60` (отображается округлённо как X/10),
     отсортированный по убыванию;
   - у кандидатов, которых уже выгружали — бейдж «уже передан»;
   - на каждого кандидата — кнопка «выгрузить карточку»; отдельно — «выгрузить список»
     (пачкой, переиспользует существующий `export/`, E9-03).
3. HR правит текст портрета → «Сохранить»:
   - backend создаёт новую версию `VacancyProfile` (`create_vacancy_profile_version`,
     уже есть, E1-07) — это уже триггерит `enqueue_fit_recalc_for_course` (E7-04) для
     уже проанализированных кандидатов;
   - **плюс новый вызов** `enqueue_full_screening_for_course(course_id)` — ставит
     `AIProcessingJob` на **всех** кандидатов курса, включая тех, кто ещё ни разу не
     анализировался по этой вакансии.
4. Модалка закрывается сразу после сохранения — **без живого обновления прогресса**
   (согласовано явно). Существующий scheduler (E5-04, тик каждые 30 мин) разбирает
   очередь как обычно.
5. HR открывает модалку позже — видит обновившийся список по `GET
   .../candidates/screening/`.
6. Выгрузка карточки (одной или списком) автоматически помечает кандидата(ов) как
   «передан» — не требует отдельного действия от HR.

Существующий CLI `run_full_course_screening.py` (E10) не меняется — остаётся
независимым инструментом для ручных прогонов без UI.

## Данные

Новая таблица `CandidateVacancyTransfer` (репозиторий `SFERA-AI`, Alembic-миграция):

| Поле | Тип | Комментарий |
|---|---|---|
| `id` | PK | |
| `candidate_profile_id` | FK → `CandidateProfile` | |
| `course_id` | Integer | id курса на платформе (как в остальных вакансийных джобах) |
| `transferred_at` | timestamp | когда впервые выгружен |

Уникальный индекс на `(candidate_profile_id, course_id)` — повторная выгрузка не
дублирует запись, просто ничего не делает (или обновляет `transferred_at`, решить на
шаге реализации — не блокирует дизайн).

Отдельная таблица, а не поле на `CandidateVacancyAnalysis` — статус «передан» не должен
сбрасываться при пересчёте fit / появлении новой версии анализа (у `CandidateVacancyAnalysis`
своя версионная история, `is_current` меняется при каждом пересчёте).

Отображаемая шкала 6–10 в UI — **только форматирование**: `round(fit_score / 10)`.
Внутри всё остаётся на шкале 0–100 (`fit_score` — `SmallIntegerField`, как сейчас).
Порог показа в модалке — `fit_score >= 60`.

## API (репозиторий `SFERA-AI`, слой `E8 Read API`)

- **`GET .../candidates/screening/`** (новый) — кандидаты курса с `fit_score >= 60`,
  сортировка по убыванию `fit_score`. Каждая запись — как в существующем `candidates/`
  списке (E8-02) + новое поле `transferred: bool` (join на `CandidateVacancyTransfer`).
- **`POST .../vacancy-profile/`** (существует, E8-04) — контракт не меняется. После
  `create_vacancy_profile_version` добавляется второй вызов —
  `enqueue_full_screening_for_course(course_id)` — рядом с уже существующим
  `enqueue_fit_recalc_for_course`.
- **`POST .../export/`** (существует, E9-03) — после успешной сборки архива добавляется
  побочный эффект: upsert в `CandidateVacancyTransfer` для всех кандидатов, попавших в
  экспорт (один или несколько).

## Новая сервисная функция

`enqueue_full_screening_for_course(session, course_id)` — новая функция в
`src/sfera_ai/services/job_detection.py`. По образцу перебора `Application` из
`run_full_course_screening.py` (E10-01): для каждого кандидата курса —
`resolve_or_create_candidate_profile` (если профиля ещё нет) + постановка джобы через
уже существующий `_create_job_if_absent` (дедуп: не дублирует уже стоящую `PENDING`
джобу того же кандидата). Дальше существующий scheduler/воркер (E5-04) сам гоняет
обычный пайплайн (resume → facts → fit) — новый код ничего не знает про сам скоринг,
только ставит джобы.

## Frontend (репозиторий `SPHERA`)

**Другой репозиторий — требует отдельного явного разрешения владельца перед стартом**
(правило `CLAUDE.md` этого проекта, как и весь эпик E14).

- Кнопка «Обработка кандидатов» — в разделе кандидатов конкретного курса, рядом с
  «Выгрузить архив» (не глобально, не отдельный раздел).
- Модалка: textarea портрета + список из `GET .../candidates/screening/`, кнопки
  экспорта (одиночный/массовый).
- «Сохранить» → `POST .../vacancy-profile/` → закрыть модалку немедленно, без поллинга
  статуса.

## Edge cases

- Открыли модалку только посмотреть список, портрет не трогали — «Сохранить» не жали →
  новых джоб не ставим, GET ничего не запускает, только читает текущее состояние.
- Нет ни одного кандидата с `fit_score >= 60` — модалка показывает пустое состояние, не
  ошибку.
- Кандидат без резюме (уже покрыто E13 — «нет резюме» не блокирует, только снижает
  уверенность) — попадает в список на общих основаниях, если fit ≥ 60.
- Повторное «Сохранить» без реальных правок текста — `create_vacancy_profile_version`
  создаст новую версию в любом случае (существующее поведение E1-07, не меняем в рамках
  этого дизайна); UX-предупреждение «текст не менялся» — вне объёма, можно обсудить
  отдельно на шаге фронтенда.
- Повторная выгрузка уже «переданного» кандидата — не ошибка, просто повторно
  проставляет/подтверждает `transferred_at`.

## Вне объёма этого дизайна

- Живое обновление прогресса обработки в модалке (осознанно отклонено — «без живого
  обновления»).
- UX-предупреждение о бессмысленном пересохранении портрета без изменений.
- Изменение шкалы `fit_score` в БД/промпте (осталась 0–100, 6–10 — только отображение).
- Сам E14-06 (транскрипт/summary видео в карточке ответа кандидата) — отдельный шаг,
  не пересекается с этим дизайном.
