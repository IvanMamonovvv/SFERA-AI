# Шаг E6-04 — включение реальных AI-вызовов в очередь (снятие dry-run)

**Статус:** DONE
**Слой:** Backend · **Зависит от:** E5-04, E6-01, E6-03
**Перед началом:** прочитай `03_TDD.md` «7. Риски» → Cost Protection (все 6 пунктов).

## Цель

`process_batch` (E5-04) вместо dry-run-заглушки реально вызывает
`build_or_update_candidate_facts` (E6-01) и/или `fit_scoring` (E6-03) в зависимости от
`reason` джобы — впервые в проде тратится AI-бюджет.

## Что сделать

0. **Перед снятием dry-run** — прикинуть реальную стоимость на кандидата: собранный
   промпт E6-03 (`facts` + `requirements` + `VacancyMemory`) прогнать на 5-10 реальных
   профилях через `providers.py`, посчитать `tokens_input`/`tokens_output`/`cost_estimate`
   по факту (не по грубой оценке из E5-04/step-E5-04-scheduler-dry-run.md — там оценка
   была только по резюме-экстракции E3, не по fit-scoring промпту, который больше).
   Умножить на реальный лимит очереди (`ai_analysis_max_concurrent_jobs`) × частоту тика
   из E5-04 — получить оценку $/сутки при полной нагрузке. Показать владельцу перед
   пилотом, не после.
1. Диспетчер по `reason`: профильные reason'ы → E6-01, вакансийные → E6-03 (E5-03
   логика уже разделяла уровни детекции).
2. Флаг `AI_PROCESSING_DRY_RUN` снимается **только для ограниченного пилота** (сначала
   один `course`, явно согласованный с владельцем) — не глобально сразу.
3. Идемпотентность на входе джобы: заново вызвать E5-02 detection — если условие уже не
   истинно, `DONE` без AI-вызова (защита от гонки/повторного тика).

## Файлы

- `src/sfera_ai/services/job_processing.py` — расширение диспетчера

  только когда detection всё ещё истинна на момент обработки

## Критерии готовности (DoD)

- [x] Джоба с уже неактуальным условием — `DONE` без AI-вызова (тест с моком, счётчик
      вызовов == 0)
- [x] Пилот ограничен одним `course`, явно подтверждённым владельцем перед запуском на
      проде — механизм готов (`pilot_course_id`) и **доказан реальными вызовами**
      (`course_id=25`, п.0 стоимость + E6-05 сверка). Сам флаг `ai_processing_dry_run`
      для автоматической обработки через очередь не снят — планировщик (`scheduler.py`)
      ещё не задеплоен на проде как постоянный процесс (`Dockerfile` CMD — временный
      `smoke_test`, реальный entrypoint — предмет E8, `05_EPICS.md`); включать флаг раньше
      деплоя бессмысленно и рискованно. Отложено на E8 — там перед первым автозапуском
      тика нужно отдельное «ок» от владельца.
