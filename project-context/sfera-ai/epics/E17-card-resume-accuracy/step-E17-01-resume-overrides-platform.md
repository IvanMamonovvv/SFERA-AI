## Контекст (важное отличие от исходной формулировки владельца)

Изначально запрос звучал как «резюме должно подменять платформенные данные, если они
неверны». По факту в коде это НЕ два независимых источника с явным приоритетом —
`profile.facts` уже единый список, куда `_resume_facts` (из `ResumeExtract`,
`source_type` HH_RESUME/ANKETA_FILE) и `_answers_facts` (LLM-экстракция из анкеты,
`source_type` ANSWER) пишут факты с одинаковыми ключами (`experience_years`,
`positions`, `companies`) без дедупа между источниками (`_dedupe_key` учитывает
`source_type`, поэтому один и тот же ключ от разных источников не считается дублем и
остаётся в списке дважды).

`_fact_value(facts, key)` (`ai_card.py:134`) при рендере карточки берёт **первое
совпадение по ключу** — то есть чей факт оказался раньше в списке по случайному
порядку добавления (зависит от того, что было обработано раньше по времени: анкета
или резюме), а не по надёжности источника. Это и есть реальная причина, почему
владелец увидел на карточке значения, не совпадающие с тем, что ожидалось от резюме —
приоритет резюме>ответы>видео (E13-01) в промпте LLM уже есть, но к пикингу значения
для самого отображения (`_platform_block`/`_meta_bar`/`_header_block`) не применялся
никогда.

Отдельно: `phone_number`/`city` — ключи, которые сейчас производит **только**
`_answers_facts` (анкета). `_RESUME_FACT_KEYS` (`candidate_facts.py:25`) не включает
эти два поля — `resume_extraction.py:_SYSTEM_PROMPT` их не запрашивает у LLM вовсе.
Значит для этих двух конкретных полей (телефон, город — то, что на скриншоте владелец
видел «платформенным») сегодня физически нет резюме-версии для сравнения/подмены.

## Цель

При рендере карточки (и в других местах, где код читает `profile.facts` по ключу)
при наличии нескольких фактов с одинаковым `key` от разных источников выбирается
факт с более приоритетным источником (HH_RESUME/ANKETA_FILE > ANSWER > VIDEO), а не
первый по порядку добавления.

## Что сделать

1. **Согласовать с владельцем перед кодом**: включать ли `phone_number`/`city` в
   список полей, которые извлекает резюме-LLM (`resume_extraction.py:_SYSTEM_PROMPT`)?
   Без этого шага телефон/город остаются исключительно платформенными (ответы анкеты),
   расхождение с резюме для них некому обнаруживать. Если владелец подтверждает —
   добавить в `_SYSTEM_PROMPT` + `_RESUME_FACT_KEYS`.
2. `_fact_priority(source_type: str) -> int` (или похожий helper) в
   `candidate_facts.py` рядом с `_dedupe_key` — HH_RESUME/ANKETA_FILE выше ANSWER выше
   VIDEO/неизвестного.
3. Заменить `_fact_value` в `ai_card.py` на выбор факта с максимальным приоритетом
   среди всех совпадений по ключу (сохранить сигнатуру и внешнее поведение, если
   совпадение только одно).
4. Проверить остальные точки использования `_fact_value`-подобной логики (`api_read.py`
   — если там тоже читаются `facts` по ключу для API) — не дублировать разную логику
   пикинга в разных местах, вынести общий helper, если конфликт возможен там же.
5. Не трогать `_dedupe_key`/структуру хранения `profile.facts` — оба факта (резюме и
   анкета) должны оставаться в списке для истории/аудита, приоритет — только на этапе
   выбора значения для отображения.
