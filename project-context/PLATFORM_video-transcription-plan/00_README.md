# Транскрибация и summary видеовизиток кандидатов

> Точка входа фичи. Статус — `01_STATE.md`. Технический контекст (где что в коде, ограничения) — `02_CONTEXT.md`.
> Каждый шаг — отдельный файл `step-XX-*.md` с подробными действиями и журналом.

## Цель

Как только кандидат загружает **видеовизитку** (ответ типа `VIDEO_RECORDING`, файл в S3 Timeweb),
система **автоматически, фоном**:
1. извлекает аудио из видео,
2. **транскрибирует** речь в текст,
3. по расшифровке делает **итоговое summary + вердикт** («целевой / нецелевой / данных нет»),
4. показывает всё это HR/админу в карточке кандидата (`domains/Candidate/`).

**Обрабатываются ВСЕ видеовизитки без исключения** — даже если кандидат записал 1 секунду тишины,
закрыл камеру рукой или молчал. В этом случае транскрипт пустой → summary явно пишет:
«Кандидат ничего не сказал / речь не распознана → вероятно нецелевой». Пустой результат — тоже результат.

## ⚠️ Что транскрибируем, а что НЕТ (граница scope)

В системе **два разных типа видео** — обрабатываем только один:

| Видео | Модель / путь | Кто грузит | Транскрибируем |
|---|---|---|---|
| **Видеовизитка кандидата** | `Answer` c `question_type=VIDEO_RECORDING`, файл в `answer_file/` | Кандидат в уроке | ✅ **ДА** |
| **Видео в уроке** (собственник, презентация; до 15 мин) | `LessonMedia`, путь `course_media/…` (фича `admin-lesson-video`) | HR / админ | ❌ **НЕТ** |

Триггер (step-02) стоит **исключительно на `Answer` с типом `VIDEO_RECORDING`**. Видео уроков (`LessonMedia`)
идут по другому пути загрузки и в очередь не попадают. **Не привязывать транскрибацию к `LessonMedia` /
video_processing уроков** — иначе начнём зря молоть 15-мин видео собственника.

## Не-цели (сознательно вне scope волны 1)

- Оценка кандидата по содержанию резюме/тестов (только по видео).
- Реалтайм: обработка асинхронная, HR видит результат через 1–5 мин после загрузки, не мгновенно.
- **Анализ мимики/эмоций по лицу — сознательно НЕ делаем в волне 1.** Технически возможно
  (facial emotion recognition), но: спорная научная база (ненадёжные выводы), юр./этический риск найма
  по биометрии (152-ФЗ, предвзятость), тяжёлая инфра (разбор кадров, ML/GPU — уже не «0₽ на недогруженном
  сервере»), низкий ROI. Ценность — в словах кандидата (транскрипт+LLM). Вернуться можно отдельным
  экспериментом, осознанно.

## Ключевые решения (согласовано с владельцем)

| Вопрос | Решение | Почему |
|---|---|---|
| **Где транскрибировать** | **Self-hosted `faster-whisper`** в отдельном воркер-контейнере | 0₽/видео, нет геоблока (сервер в РФ, прямой OpenAI недоступен), уже есть изоляция от веба |
| **Нагрузка на сервер** | Транскрибация только в **отдельном процессе-воркере**, НЕ в веб-воркерах | Веб для пользователей не просаживается при обработке |
| **Пики и завалы (5 / 50 / 200 разом)** | **Очередь задач в БД** (`TranscriptionJob`) + пул воркеров с `SELECT FOR UPDATE SKIP LOCKED` | Без Celery/Redis; отклики мгновенно ставятся в очередь, воркеры дренируют фоном |
| **Число параллельных обработок** | env `TRANSCRIBE_CONCURRENCY` (по числу свободных ядер) | Тюнится под реальный VPS после бенчмарка (step-00) |
| **Summary** | Дешёвый LLM: **GigaChat Lite** (нативный РФ) или GPT-4o-mini через РФ-прокси | ~0.05–0.1₽/кандидат, качество на русском достойное |
| **Страховка** | Транскрибация и summary спрятаны за интерфейсы `*Provider` с env-переключателем | При росте нагрузки — переключение на Yandex SpeechKit / прокси **одной переменной**, без переписывания |

## Архитектура (как это работает)

```
Кандидат загрузил видеовизитку (Answer VIDEO_RECORDING + файл в S3 Timeweb)
        │  (сигнал на сохранении видеоответа, step-02; перезапись → пере-обработка)
        ▼
  TranscriptionJob(status=PENDING)  ← мгновенная вставка в БД, веб не блокируется
        │
        ▼   отдельный контейнер: python manage.py run_transcription_worker
  ┌─────────────────────────────────────────────┐
  │ worker loop (concurrency = N ядер):          │
  │  SELECT ... FOR UPDATE SKIP LOCKED  (пачка)  │
  │  1. скачать файл из S3 (или локальный диск)  │
  │  2. ffmpeg: видео → wav (аудиодорожка)       │
  │  3. TranscriptionProvider → transcript_text  │
  │  4. SummaryProvider(transcript) → summary +  │
  │     verdict (в т.ч. «пусто → нецелевой»)     │
  │  5. status=DONE, сохранить в БД              │
  └─────────────────────────────────────────────┘
        │
        ▼
  HR/Admin: карточка кандидата → бейдж статуса +
            транскрипт (сворачиваемый) + summary + вердикт
```

## Экономика (главное)

Средняя видеовизитка ≈ **3 минуты**.

| Статья | Self-hosted (по умолчанию) | Cloud-fallback (если понадобится) |
|---|---|---|
| Транскрибация 3-мин видео | **0₽** (только CPU-время воркера) | Yandex SpeechKit ~1.8–3₽ / Whisper-прокси ~1.5₽ |
| Summary (LLM, короткий транскрипт) | ~0.05–0.1₽ | ~0.05–0.1₽ |
| **Итого на кандидата** | **≈ 0.1₽** | **≈ 2–3₽** |
| 1000 кандидатов/мес | **≈ 100₽** (только summary) | ≈ 2000–3000₽ |

Разовые затраты self-hosted: место под модель (`small` ~0.5 ГБ, `medium` ~1.5 ГБ на диске),
пик ~1–1.5 ГБ RAM на воркер во время обработки. **Проверяется в step-00 на реальном VPS.**

### Факт: характеристики VPS (Cloud MSK 80)

`4 × 3.3 ГГц CPU · 8 ГБ RAM · 80 ГБ NVMe · Ubuntu 24.04`.

**Факт по мониторингу за месяц (риск снят):**
- **CPU почти простаивает** — обычно < 20%, пики до ~25%. Огромный запас под транскрибацию.
- **RAM: реально занято ~2 ГБ** (остальное до 5–7 ГБ — освобождаемый кэш Linux). **Свободно ~6 ГБ.**
- **Диск:** занято 27 из 80 ГБ — место под модель есть.

Вывод: сервер недогружен, self-hosted — с околонулевым риском.
- **Выбор модели: `small`** (~0.7–1 ГБ/процесс) по умолчанию. `medium` (~1.5–2 ГБ/процесс) теперь тоже
  реально помещается (~4 ГБ при c=2 против ~6 ГБ свободных) — опция про запас, если качество `small` не устроит.
- **Параметры по умолчанию:** `WHISPER_MODEL_SIZE=small`, `TRANSCRIBE_CONCURRENCY=2` (можно 3, CPU простаивает),
  воркер-контейнер с лимитами `cpus: 2` + `mem_limit` (гигиена, не необходимость).
- Пропускная способность: ~80 видео/час; завал 200 → ~2.5 ч фоном.
- step-00 теперь — подтверждение цифр и проверка качества модели на русском, а не проверка «выдержит ли».

## Жёсткие ограничения (нельзя нарушать)

- ⚠️ **`clean_expired_videos()` удаляет видеоответы через 30 дней** (`core/scheduler.py`). Транскрипт+summary
  ОБЯЗАНЫ быть сохранены в БД до удаления файла (step-08).
- Транскрибация **только в отдельном процессе**, никогда в веб-запросе (иначе просадка платформы).
- Файлы видео — в S3 Timeweb при `USE_S3_STORAGE=true`, иначе локальный диск. Провайдер должен работать в обоих режимах (storage-API Django).
- Не ломать существующий поток ответов/попыток (`testchecks/`), только дополнять.
